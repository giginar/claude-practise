Claude Certified Architect – Foundations (CCAR-F) Exam Notes

Domain 1: Agentic Architecture & Orchestration
Agentic Loop and Core API
What is the only reliable signal to terminate an agentic loop?
Checking if the stop reason form the API is exactly “end turn”
What two things must be appended after each tool call?
You have the appended original assistant message and the brand-new user message that holds the result from that tool.
The exam’s most common trap: parsing text! The answer is always “stop_reason”.
Multi Agent Orchestration
If you want a coordinator to spawn subagents what allowedTools must be included?
The ‘task’ tool.
How do you run two agents at the same time?
You make sure both of the task_tools calls are omitted from the single response from the coordinator.
What is the only context that a subagent should receive?
Only the context specific to its assigned subtask.
You have a new subagent to test, but you don’t want to risk messing up your main conversation, what to use?
fork_session
Hooks Programatic Enforcements
If a rule must be enforced 100%, use a hook. Prompt enforcement is always wrong.
Which of your rules are too critical to be left to a prompt?
The answered rules needs a deterministic hook.
Session Management Workflows
Is the next step determined by the PLAN or the RESULT?
PLAN -> Chaining Prompt, RESULT -> Dynamic Adaptive
When to use fork_session vs —resume?
fork_session: experimental sandbox(not effects main chat but inherits full history)
—resume: effects main chat, inherits full history.
What is stale context and how do you migitate it?
Stale Context: Data retrieved early in the session that may become outdated by the time it is used. Solution: re-fetch critical data immidiately BEFORE the action that uses it.
Domain 2: Tool Design & MCP Integration
Tool Description Best Practices
Exam Tip: The most detailed answer is always the right answer.
What are 6 key things to make a great tool description?
A Clear Purpose: 1 simple sentence what is this tool do,
Input specs: what are the exact types rules formats for the data,
Examples: show it how its done,
Edge cases: what happens empty or weird data
Tell it when not to use it,
Clear description of return value not for success only, but for a  not found situation too.
Why does the detail matter in a tool description?
Because Claude literally uses these descriptions to figure out what to do. Vague descriptions cause wrong selection, missed edge cases and unexpected behavior.
What should you document about return values?
Document both the successful result and the empty and no-result mean and super clear about empty result means not found not an error.
Structured Error Responses
What 4 fields must a structured error response must have?
isError: boolean
ErrorCategory: string
isRetryable: boolean
Context: string
What is the single most important difference in the response for ‘access failure’ and ‘empty result’?
isError flag, access failure is true.
When is isRetryable true and false?
True for temporary transient errors that can just fix themselves. Set it to false for permanent errors like a bad password.
Exam Tip: If the questions says ‘database is unavailable’ or ‘connection failed’; returning [] is always wrong, return isError: true.
Tool Distribution Selection
What is the magic number of tools for an agent?
4-5. 6-10 is acceptable. More is confusing.
How do you force a specific tool to be used?
tool_choice option.
“Auto”: model decides which tool to use, default, general purpose
“Any”: model must use a tool, it chooses which, general tool invocation
{“type”:”tool”,”name”:”X”} -Z you force the model for the exact tool.
Exam Tip: When exam shows 18 oops on one agent, the right answer is always ‘distribute across subagents’.
MCP Server Configuration
.mcp.json -> project level scope, shared via git, purpose: team tools-project integration
/.claude.json -> user level scope, personel-not shared, purpose: individual credentials, personal tools
What’s the biggest mistake you can make in .mcp.json?
Hardcoded secrets are a major security risk. Use environment variables ( ${ENV_VAR} ) to securely load secrets at runtime.
Exam Tip: Any answer hardcoding API keys in .mcp.json is always wrong. Use ${ENV_VAR} syntax.
Builtin Tools
Six builtin tools:
read: read file contents;  use case: config files, code review
Write: create new files from starch; new files only, replaces existing files
Edit: modify existing files; targeted bug fixes, feature additions
Bash: execute shell commands; npm test, built systems, installs
Grep: search inside files for text; find all usages of a function
Glob: files based on their name pattern; find all *.text files
Exam Tip: The exam often shows Bash(“cat file.txt) or Bash (Grep -r ….). Correct answer replaces these with Read() and Grep()
When is Bash the tool choice?
- Execution
Is there a specific built-in tool design for the exact operation?
If yes, use it. If not, then maybe it’s Bash.
Domain 3: Claude Code Configuration & Workflows
Claude MD Hierarchy
User Level -> ~/.claude/CLAUDE.md; not in git; personal keybindings or favorite color layout
Project -> .claude/CLAUDE.MD; in git; typescript rules
Directory -> src/api/CLAUDE.MD; module scoped; API Auth rules
A rule defined in specific directory always overrides a more general project rule.
@import directive -> includes external md files for modular config. Keeps files focused and maintainable. Important for Modularity for clean, logical, manageble pieces.
AntiPattern -> A massive MD file or mixing personal preferences into a shared config.
Custom Command Skills
Commands: quick and dirty shortcuts. Runs in current session, tool access can not be restricted. Location: .claude/command/*.md
Skills: orchestration complex, multistep behaviors. Con fork context, toll accesss can be restricted. Location: .claude/skills/name/SKILL.md
SKILL.md -> context: fork -> creates isolated execution environment, preventing pollution of the main session, allowed_tools: […] -> restricts the skill to a specific list of tools, preventing accidental operations.
AntiPattern -> create a powerful skill, but forget to add allowed_tools, this gives the skill wide permissions, avoid it!
Exam Tip: Task needs isolation or tool restriction use ‘SKILL’. If it is a simple shortcut, use ‘command’.
Plan Mode Iterative Refinement
Plan Mode -> When to use: Multi file architecture, unknown scope, expensive to undo; Behavior -> Outlines approach before executing
Direct Execution Mode -> When to use: Simple well defined, single file tasks; Behavior -> Executes immediately, no overhead
TDD (preferred refinement pattern)-> 1. Write test -> 2. Run(fails) -> 3. Implement -> 4. Run(passes) -> 5. Refine
AntiPattern -> Plan mode for simple tasks, Direct execution for multi-file architectural changes, vague refinement feedback such as “make it better”
CICD Batch Processing
-p -> purpose: non interactive mode; Exam note: always required for CICD
—output-format json ->  purpose: structured json output; Exam note: for automated downstream processing
—json-schema -> purpose: enforce output json shape; Exam note: guaranteed specific json structure
AntiPattern: In the same session, where code generated, making a review will create a confirmation bias.
Synchronous API: Immediate, cost is normal, use case: blocking PR review, real-time feedback
Message Batch API: within 24h, cost Is %50 saved, use case: nightly audits, weekly scans
Domain 4: Prompt Engineering & Structured Output
Explicit Criteria Instruction Design
AntiPattern: “Be thorough and find all issues” - no scope, no boundary; “improve the code” - improve how? No measurable success criteria.
The difference between a vague prompt and an explicit one is clarity and control.
The correct criteria prompt will always be scoped, specific, structured and measurable with something like a control checklist.
What is “alert fatigue”?
Too many false positives cause developers to ignore all flags, including the real ones.
What is the benefit of explicit criteria?
It is all about getting consistent, automatable results with a low rate of false positives, which builds developers trust.
Few Shot Prompting
Why is few-shot prompting important?
Providing examples in the prompt to teach the model a specific task, format or style.
How many examples?
0 -> zero shots: simple, objective tasks.
2-4 -> OPTIMAL: ambiguous, custom formats
5-6 -> Acceptable: complex edge cases
7+ -> Diminishing: bloats prompt & cost, avoid.
Examples should have exact same format(json etc..), category diversity, edge case coverage (at least 1 edge example)
When is the few-shot most valuable and it shines?
Ambiguity or when you need a specific output format, anytime lines between the categories are fuzy.
Structured Output Tool Use
What does tool_use actually guarantee?
All required fields present, correct types, valid enums. I does not guarantee the values, dates, totals inside.
The key is forcing the tool call, then immediately validating the output.
AntiPatterns: assuming tool_use does all the work, without checking the values, writing to db.
Why is it a good idea to include “other” category in your schemas enums?
It is a safety net, if something does not fit, it will go there, so hallucinating will be eliminated.
Validation Retry Loops
An automated quality check process that validates output immediately and re-prompts the model with specific targeted feedback on errors.
AntiPatterns: generic retry (there is an error, try again. Model needs to know what to fix); same session development and review; don’t look big picture accuracy number, there can be a failure in one specific area (receipts are always correct but maybe invoices are always wrong)
Exam Tip: Always retry with specific feedback, avoid same session review, use stratified metrics.
Domain 5: Context Management & Reliability
Context Optimization Positioning
Case Fact Patterns: immutable, structured reference block you place at the start of the context. never summarize the block, don’t compress it, and reference it directly in your prompts.
Exam Tip: Preserve critical details via case fact blocks. Progressive summarization always loses information. Case fact blocks = always correct.
What is the progressive summarization risk?
The risk is repeated compression ends up losing critical details, names, IDs, amounts; solution is immutable case fact blocks instead.
What is “the loss in the middle” effect?
Information stuck in the middle of the long context is least likely to be called by the model, because of that place the critical data at the start at the start like case facts or at the end like the current task.
In system design, losing facts isn’t an error; it’s a failure. Architect for integrity.
Escalation & Error Propagation
VALID: customer explicitly requests a human. This is deterministic with no ambiguity. -> trigger for human
VALID: a policy gap exists. The agent cannot safely invent a new rule. -> trigger for human review
VALID: The task exceeds the agent’s capabilities. Its an out of scope requests -> escalate
VALID: if over $50 need human approval. Deterministic -> trigger for human escalation
AntiPattern: amodels self-reported confidence report, it is just an internal report, the solution may be right.
Exam Tip: Sentiment-based and confident-based escalation are always wrong on the exam.
What are 5 valid escalation triggers?
An explicit customer request, a policy gap, the task exceeds the agent’s capabilities, a business trash hold met, repeated failures after recovery attempt.
What are the big three anti-patterns?
Negative customer sentiment, models self reported low confident, a long conversation duration
What is the number one rule for error propagation?
Never ever silently drop failures, you must always report what happened rich structured context so the system make an intelligence choice.
Context Degradation Extension Sessions
Context Degradation: Performance diminishes as conversation history grows, potentially losing track of critical informaiton.
4 main solutions:
/compact: compress conversation history to reclaim context space. When to use: context is getting long, but the task is not yet done.
Strachpad files: persist critical state to external files that survive a reset. When to use: you’ve uncovered important intermediate findings.
Subagent delegation: a subagent absorbs verbose “noise” from exploration. When to use: The main coordinator’s context needs to stay clean.
Position-aware ordering: Places critical data at the start/end. Less important data in the middle. When to use: You are dealing with long contexts of mixed importance.
Exam Tip: Aggregate metrics mask failures. Always track per-category.
Human Review Information Provenence
Source: where did the date come from?
db, invoice
Confidence: how reliable is this source?
Verified Data -> Extracted Data-> Inferred Data-> Estimated Data (confidence hierarchy)
Retrieved_at: when was is fetched?
Enables staleness detection
Agent_id: which subagent provided it?
Enables tracing conflicts
AntiPattern: arbitrarily pick one, ignore the conflict -> automatic wrong answer.
Exam Tip: When subagents conflict: always use provenance to resolve. “Just pick one” is always wrong.

Quizes

1. PreToolUse Hooks – Regex Matching
Regex matchers without anchors (e.g., /refund/) match any tool name containing the substring, including issue_refund_note. Use ^ and $ for exact matching (/^refund$/) or a literal matcher (refund) to target only the intended tool.
2. Claude Code CLI – Non-Interactive Mode
When running Claude Code in CI/CD environments (e.g., GitHub Actions), always use -p (--print) to enable non-interactive execution. Without -p, Claude starts an interactive session and may hang waiting for terminal input until timeout.
3. Skills – argument-hint
The argument-hint field in SKILL.md frontmatter displays expected arguments in the slash-command autocomplete menu (e.g., argument-hint: [issue-number]). It improves usability without changing skill execution or validating arguments.
4. Agentic Loop – Model-Driven Decisions
After a tool executes, append its tool_result to the conversation and send it back to Claude. This allows Claude to independently decide whether to retry, call another tool, or finish, instead of relying on hardcoded application logic.
5. MCP Servers – Reserved Names
Claude Code reserves certain MCP server names, including computer-use, workspace, and claude-in-chrome. Custom MCP servers using reserved names are rejected or skipped, so they must use unique names.
6. PostToolUse Hooks – Output Replacement
Use updatedToolOutput in PostToolUse hooks to replace tool output for both built-in and MCP tools. The legacy updatedMCPToolOutput field only supports MCP tools, while additionalContext adds information rather than replacing output.
7. CLAUDE.md – File Imports
Using @path/to/file in CLAUDE.md imports the referenced file's contents into context. Wrap the path in backticks (e.g., @docs/legacy-notes.md) to display it as literal text without triggering an import.
8. Structured Outputs – False Positive Analysis
Add a detected_pattern field to structured findings to record the specific code construct or pattern that triggered each detection. This enables grouping dismissed findings by pattern, identifying false-positive trends, and improving detection accuracy.
9. PreToolUse Hooks – permissionDecision
PreToolUse hooks support three permission decisions: allow (execute automatically), ask (request human approval), and deny (block execution). Use allow for low-risk read-only operations (e.g., masked order history) and ask for high-risk irreversible actions (e.g., refunds), with identity verification enforced separately when required.
10. Research Pipeline – Parallel Subagent Execution
For independent tasks (e.g., analyzing multiple legal precedents), the coordinator should spawn parallel subagents and aggregate their results before synthesis. Keeping orchestration at the coordinator level improves latency, observability, debugging, and control compared to allowing subagents to spawn nested agents.
11. Customer Support – Resolution Before Escalation
When a customer requests human support but the issue is already confirmed as immediately resolvable, acknowledge their frustration and offer to resolve it directly or escalate. Do not automatically escalate when a verified solution is available, but respect the customer's choice.
12. Tool Choice – Enforcing Tool Execution Order
Use tool_choice: {"type": "tool", "name": "extract_metadata"} to force a specific tool call when prerequisite data must be extracted first. After receiving the result, allow subsequent turns to call dependent tools; forcing the same tool on every API request prevents the workflow from progressing.
13. Code Exploration – Tracking Function Aliases
When finding all callers of a function, first inspect its definition and wrapper modules to identify aliases, re-exports, and renamed references. Then use Grep to search for every exposed name across the codebase, rather than searching only for the original function name.
14. Structured Extraction – Handling Amendments
Design extraction schemas to preserve multiple values for amended fields, including their source locations and effective dates. This enables the system to distinguish original terms from amendments and determine which value is currently applicable instead of arbitrarily selecting one.
15. Structured Extraction – Preventing Hallucinated Values
Explicitly instruct Claude to return null when information is not directly stated in the source document, even if a plausible value could be inferred. Nullable JSON schema fields alone do not prevent hallucinations; prompt instructions must enforce evidence-based extraction.
16. Code Exploration – Incremental Architecture Discovery
For understanding large codebases, start with targeted Grep searches to locate relevant entry points, then follow imports, function calls, and dependencies incrementally. This approach minimizes unnecessary context consumption and builds an accurate architectural understanding without exploring unrelated services.
17. Research Pipeline – Dynamic Subagent Routing
The coordinator should assess each query's complexity and dynamically select only the subagents needed to complete it. Simple factual questions may require one agent, while complex research may need multiple agents, avoiding both unnecessary execution and rigid routing rules.
18. Structured Extraction – Confidence-Based Human Review
Have Claude produce field-level confidence scores and calibrate review thresholds using a labeled validation dataset. Prioritize low-confidence extractions for human review, since semantic errors can pass JSON schema validation even when all required fields are present.
19. Customer Support – Clarification Before Escalation
When a frustrated customer requests immediate human support but the issue has not yet been investigated, acknowledge their frustration and ask one targeted question to identify the problem before escalating. Avoid unnecessary investigation or repeated questions, and honor an explicit escalation request if the customer insists.
20. Code Exploration – Dynamic Task Decomposition
For debugging complex issues (e.g., intermittent HTTP 500 errors), dynamically generate investigation subtasks based on findings from each exploration step. Follow the actual execution path through routing, middleware, business logic, and database layers instead of assigning fixed parallel investigations before understanding the problem.
Exam 1
Key lessons from the mistakes in the first practice exam. Each note focuses on the idea that would help identify the correct answer next time.
1. max_tokens Is Not a Normal Finish
If stop_reason is max_tokens, Claude did not finish the response. Increase max_tokens and retry so you can receive the complete tool call or answer. The key is to treat max_tokens as an incomplete run, not as success.
2. Detect Completion from SDK State, Not Text
Do not decide that an agent finished because its text contains a phrase such as “Research complete.” Use the Agent SDK termination state instead. A success subtype means the loop ended normally, while error_max_turns means the run stopped because it hit the turn limit.
3. Human Escalation Needs Provenance
When sources conflict, the human reviewer needs a short structured handoff, not raw agent transcripts. Include each conflicting value, its source and date, what checks were already performed, and a suggested next step. The main idea is to make the conflict easy to verify quickly.
4. Parallelize Independent Questions
If one request contains independent research questions, split them into separate subtasks. Give each subagent the shared background it needs and launch the Agent tool calls in the same coordinator response. This improves depth and reduces latency compared with one agent doing everything.
5. Existing MCP for Standard Services, Custom MCP for Proprietary APIs
Use an existing MCP server when the integration is common and already supported, such as Jira. Build a custom MCP server when the system exposes a proprietary API with no suitable public server. The exam is testing whether you choose reuse versus custom integration correctly.
6. Use Path-Scoped Rules for File-Specific Conventions
If a rule should apply only to certain file types, place it in .claude/rules/ and use paths globs in the frontmatter. Keep one shared rule file instead of copying the same conventions into many folders. Use claude --debug to confirm the YAML frontmatter is parsed correctly.
7. Broken Frontmatter Can Make a Rule Global
A .claude/rules/ file is only path-scoped when its paths frontmatter is valid. If the YAML is broken, the rule may load in every session. Check claude --debug for parsing errors, then verify the behavior in a fresh session before and after touching a matching file.
8. Unstated Requirements Require an Interview
If missing edge cases come from requirements nobody stated, code exploration will not solve the problem. Ask the team targeted questions and write the decisions into a self-contained spec such as SPEC.md. After the design discussion, start a fresh implementation session so the coding context stays clean.
9. Errors Must Explain Cause and Retryability
isError: true alone is not enough for good recovery. The error should clearly say what failed and whether retrying can succeed, so Claude can treat a timeout differently from a protected-branch rejection. Do not rely on a local hook for policies that frequently change on the remote system.
10. Give Interdependent Fixes Together
If several fixes depend on the same signature or architecture change, describe them together in one detailed message. Claude can then plan the shared change first and implement the dependent fixes against the new design. Sending them one by one can create unnecessary rework.
11. Missing Context Is Solved by Referencing the Existing File
If Claude keeps generating duplicate tests, the problem is usually that it cannot see the current coverage. Reference the existing test file directly with @path so its full content is in context. Plan mode does not fix missing context; it only adds a review step.
12. Use Tests as the Source of Truth for Repeated Edge-Case Breakage
When each code revision fixes one edge case but breaks another, stop relying on prose alone. Write tests for all known edge cases first, then use the failing output to guide the implementation. The stable test suite becomes the exact definition of correct behavior.
13. Personal Skills Need a Different Name
A personal skill can live under ~/.claude/skills/, but a personal skill with the same name as a project skill takes precedence. If you want to keep the team’s /review and also have your own stricter version, give yours a different command name such as /review-deep. The key detail is name precedence.
14. Batch Requests Cannot Depend on Mid-Request Client Tool Calls
If a batch request needs data from a client-executed tool during the run, redesign the workflow before using Message Batches. Perform the lookup first and include the result in the batch input. This removes the interactive dependency and keeps the request eligible for batch processing.
15. JSON Schema Checks Structure, Not Meaning
A valid schema can still contain logically wrong values, such as impossible date order or swapped parties. Add semantic validation in code for cross-field rules, then retry with the exact validation errors. The exam distinction is structural correctness versus semantic correctness.
16. Find tool_use Blocks by Type, Not Position
A Claude response can contain both text and tool_use blocks, and their order is not guaranteed. Do not assume response.content[0] is the tool result. Search for the block whose type is tool_use and read the structured data from its input field.
17. Keep Global Rules Global and File-Specific Rules Scoped
Rules that must apply to every review should stay in always-loaded project context, but they can be split into imported files to keep CLAUDE.md maintainable. Rules that only matter for certain files should move to .claude/rules/ with matching paths globs. The main decision is based on scope.
18. Repository-Wide Review Criteria Belong at the Repository Root
If a rule must apply to every pull request, do not place it in a subdirectory CLAUDE.md. Put it in the repository-root CLAUDE.md and commit it to version control. This ensures every review started in that repository receives the criteria.
19. Separate Generation and Review Contexts
An agent that audits its own work in the same resumed session can inherit confirmation bias from the migration process. Run the audit in a separate claude -p session and give it only the evidence it needs, such as the diff and project rules. Fresh context improves independent review.
20. Test a New Prompt Before a Huge Batch
A brand-new prompt should be tested synchronously on a representative sample before running it across thousands of files. This catches prompt-level problems before you pay for a large batch whose results may all be weak. custom_id resubmission is useful for scattered failures in an already-tested pipeline, not for validating an untested prompt.
21. Resumed Sessions Can Contain Stale File Knowledge
If files changed after a session was paused, do not trust the old analysis blindly. Either resume and explicitly make Claude re-read the changed files, or start a new session seeded with a structured summary of the earlier conclusions. The important idea is to refresh stale context before continuing.
