Study Guide · CCAR-F

Claude Certified Architect – Foundations Exam Notes

Concise review notes, exam tips, anti-patterns, cheat sheets, and practice-exam lessons for the CCAR-F exam.

Domain 1: Agentic Architecture & Orchestration
Agentic Loop and Core API
What is the only reliable signal for terminating an agentic loop?
Check whether the API’s stop_reason is exactly end_turn.
What two things must be appended after each tool call?
Append both the original assistant message and a new user message containing the tool result.
Common exam trap: parsing text. Always check stop_reason.
Multi-Agent Orchestration
If you want a coordinator to spawn subagents, which tool must be included in allowedTools?
The task tool.
How do you run two agents at the same time?
Include both task tool calls in a single response from the coordinator.
What is the only context that a subagent should receive?
Only the context specific to its assigned subtask.
You have a new subagent to test, but you do not want to disrupt your main conversation. What should you use?
fork_session
Hooks and Programmatic Enforcement
If a rule must be enforced 100%, use a hook. Prompt enforcement is always wrong.
Which rules are too critical to be left to a prompt?
Any must-enforce rule needs a deterministic hook.
Session Management Workflows
Is the next step determined by the plan or the result?
Plan → prompt chaining. Result → dynamic adaptation.
When should you use fork_session versus --resume?
fork_session: an experimental sandbox that does not affect the main chat but inherits its full history.
--resume: continues the main chat and inherits its full history.
What is stale context, and how do you mitigate it?
Stale context: data retrieved early in a session that may be outdated by the time it is used. Re-fetch critical data immediately before the action that uses it.
Domain 2: Tool Design & MCP Integration
Tool Description Best Practices
Exam Tip: The most detailed answer is always the right answer.
What six elements make a strong tool description?
Clear purpose: one simple sentence explaining what the tool does.
Input specifications: the exact types, rules, and data formats.
Examples: show how the tool is used.
Edge cases: explain what happens with empty or unusual data.
Usage boundaries: state when the tool should not be used.
Return values: clearly describe successful and no-result responses.
Why does the detail matter in a tool description?
Because Claude literally uses these descriptions to figure out what to do. Vague descriptions cause wrong selection, missed edge cases and unexpected behavior.
What should you document about return values?
Document successful and empty results, and clearly state that an empty result means “not found,” rather than an error.
Structured Error Responses
Which four fields must a structured error response have?
isError: boolean
errorCategory: string
isRetryable: boolean
context: string
What is the single most important difference in the response for ‘access failure’ and ‘empty result’?
isError flag, access failure is true.
When is isRetryable true and false?
True for temporary transient errors that can just fix themselves. Set it to false for permanent errors like a bad password.
Exam Tip: If the question says “database is unavailable” or “connection failed,” returning [] is always wrong. Return isError: true.
Tool Distribution Selection
What is the magic number of tools for an agent?
4-5. 6-10 is acceptable. More is confusing.
How do you force a specific tool to be used?
tool_choice option.
auto: the model decides whether and which tool to use; this is the general-purpose default.
any: the model must use a tool but chooses which one.
{"type":"tool","name":"X"}: forces the model to use the specified tool.
Exam Tip: When the exam shows 18 tools on one agent, the right answer is always “distribute them across subagents.”
MCP Server Configuration
.mcp.json: project-level scope; shared through Git; used for team and project tool integrations.
~/.claude.json: user-level scope; personal and not shared; used for individual credentials and personal tools.
What’s the biggest mistake you can make in .mcp.json?
Hardcoded secrets are a major security risk. Use environment variables ( ${ENV_VAR} ) to securely load secrets at runtime.
Exam Tip: Any answer that hardcodes API keys in .mcp.json is always wrong. Use ${ENV_VAR} syntax.
Built-in Tools
Six built-in tools:
Read: read file contents; use for configuration files and code review.
Write: create new files from scratch or replace existing files.
Edit: modify existing files; use for targeted bug fixes and feature additions.
Bash: execute shell commands; use for tests, build systems, and installs.
Grep: search inside files; use to find all usages of a function.
Glob: find files by name pattern, such as *.txt.
Exam Tip: The exam often shows Bash("cat file.txt") or Bash("grep -r …"). The correct answer replaces these with Read() and Grep().
When is Bash the right tool?
When command execution is required.
Is there a specific built-in tool design for the exact operation?
If yes, use it. If not, then maybe it’s Bash.
Domain 3: Claude Code Configuration & Workflows
CLAUDE.md Hierarchy
User level: ~/.claude/CLAUDE.md; not stored in Git; used for personal preferences.
Project level: .claude/CLAUDE.md; stored in Git; used for shared project rules.
Directory level: src/api/CLAUDE.md; module-scoped; used for rules such as API authentication conventions.
A rule defined in a specific directory overrides a more general project rule.
@import directive: includes external Markdown files for modular configuration, keeping files focused, logical, and maintainable.
Anti-pattern: Using one massive Markdown file or mixing personal preferences into shared configuration.
Custom Command Skills
Commands: quick shortcuts that run in the current session. Tool access cannot be restricted. Location: .claude/commands/*.md.
Skills: orchestration for complex, multi-step behaviors. With a forked context, tool access can be restricted. Location: .claude/skills/name/SKILL.md.
SKILL.md: context: fork creates an isolated execution environment and prevents pollution of the main session. allowed-tools: […] restricts the skill to a specific set of tools.
Anti-pattern: Creating a powerful skill without allowed-tools, which gives the skill broad permissions.
Exam Tip: If a task needs isolation or tool restrictions, use a skill. For a simple shortcut, use a command.
Plan Mode Iterative Refinement
Plan Mode: use for multi-file architecture, unknown scope, or changes that are expensive to undo. It outlines the approach before execution.
Direct Execution Mode: use for simple, well-defined, single-file tasks. It executes immediately without planning overhead.
TDD, the preferred refinement pattern: 1. Write a test → 2. Run it and see it fail → 3. Implement → 4. Run it and see it pass → 5. Refine.
Anti-pattern: Using Plan Mode for simple tasks, using direct execution for multi-file architectural changes, or giving vague feedback such as “make it better.”
CI/CD Batch Processing
-p: enables non-interactive mode; always required for CI/CD.
--output-format json: produces structured JSON output for automated downstream processing.
--json-schema: enforces a specific JSON output shape.
Anti-pattern: Reviewing generated code in the same session, which can create confirmation bias.
Synchronous API: immediate response at the standard cost; use for blocking PR reviews and real-time feedback.
Message Batches API: results within 24 hours at 50% lower cost; use for nightly audits and weekly scans.
Domain 4: Prompt Engineering & Structured Output
Explicit Criteria Instruction Design
Anti-pattern: “Be thorough and find all issues” has no scope or boundary. “Improve the code” has no measurable success criteria.
The difference between a vague prompt and an explicit one is clarity and control.
The correct criteria prompt will always be scoped, specific, structured and measurable with something like a control checklist.
What is “alert fatigue”?
Too many false positives cause developers to ignore all flags, including the real ones.
What is the benefit of explicit criteria?
They produce consistent, automatable results with a low false-positive rate, which builds developers’ trust.
Few-Shot Prompting
Why is few-shot prompting important?
Providing examples in the prompt to teach the model a specific task, format or style.
How many examples should you use?
0: zero-shot prompting for simple, objective tasks.
2–4: optimal for ambiguity and custom formats.
5–6: acceptable for complex edge cases.
7+: diminishing returns; bloats the prompt and increases cost.
Examples should use the exact same format, cover diverse categories, and include at least one edge case.
When is few-shot prompting most valuable?
When a task is ambiguous, requires a specific output format, or has fuzzy boundaries between categories.
Structured Output Tool Use
What does tool_use actually guarantee?
It guarantees that all required fields are present and that types and enums are valid. It does not guarantee that the values, dates, or totals are correct.
The key is forcing the tool call, then immediately validating the output.
Anti-pattern: Assuming tool_use does all the work, failing to validate values, and writing unchecked output to the database.
Why is it useful to include an “other” category in a schema’s enums?
It acts as a safety net: when a value does not fit the defined categories, the model can use “other” instead of inventing a category.
Validation Retry Loops
An automated quality check process that validates output immediately and re-prompts the model with specific targeted feedback on errors.
Anti-patterns: Generic retries such as “There is an error; try again,” reviewing work in the development session, and relying only on aggregate accuracy when one category may be failing.
Exam Tip: Always retry with specific feedback, avoid same-session review, and use stratified metrics.
Domain 5: Context Management & Reliability
Context Optimization Positioning
Case Fact Patterns: immutable, structured reference blocks placed at the start of the context. Never summarize or compress these blocks; reference them directly in prompts.
Exam Tip: Preserve critical details with case fact blocks. Progressive summarization always loses information. Case fact blocks are always the correct choice.
What is the risk of progressive summarization?
Repeated compression can lose critical details such as names, IDs, and amounts. Use immutable case fact blocks instead.
What is the “lost in the middle” effect?
Information in the middle of a long context is less likely to be recalled by the model. Place critical data at the beginning, as case facts, or at the end, as the current task.
In system design, losing facts isn’t an error; it’s a failure. Architect for integrity.
Escalation & Error Propagation
Valid trigger: The customer explicitly requests a human. This is deterministic and unambiguous.
Valid trigger: A policy gap exists, and the agent cannot safely invent a new rule.
Valid trigger: The request is outside the agent’s capabilities.
Valid trigger: Transactions over $50 require human approval.
Anti-pattern: Escalating based on a model’s self-reported confidence. It is only an internal report, and the solution may still be correct.
Exam Tip: Sentiment-based and confidence-based escalation are always wrong on the exam.
What are five valid escalation triggers?
An explicit customer request, a policy gap, a task beyond the agent’s capabilities, a business threshold being met, or repeated failures after recovery attempts.
What are the three main anti-patterns?
Negative customer sentiment, a model’s self-reported low confidence, and a long conversation duration.
What is the number-one rule for error propagation?
Never silently drop failures. Always report what happened with rich, structured context so the system can make an informed choice.
Context Degradation in Extended Sessions
Context degradation: performance diminishes as conversation history grows, potentially losing track of critical information.
Four main solutions:
/compact: compress conversation history to reclaim context space. Use it when the context is growing but the task is not finished.
Scratchpad files: persist critical state in external files that survive a reset. Use them after uncovering important intermediate findings.
Subagent delegation: let a subagent absorb verbose exploration noise when the main coordinator’s context must remain clean.
Position-aware ordering: place critical data at the beginning or end and less important data in the middle when working with long contexts of mixed importance.
Exam Tip: Aggregate metrics mask failures. Always track results per category.
Human Review Information Provenance
Source: where did the data come from?
For example, a database or invoice.
Confidence: how reliable is this source?
Verified data → extracted data → inferred data → estimated data.
retrieved_at: when was it fetched?
Enables staleness detection.
agent_id: which subagent provided it?
Enables conflict tracing.
Anti-pattern: Arbitrarily choosing one value and ignoring the conflict.
Exam Tip: When subagents conflict, always use provenance to resolve the conflict. “Just pick one” is always wrong.

Cheat Sheets

Domain 1: Agentic Architecture & Orchestration
The Golden Rules:
R1: Check stop_reason == "end_turn". Never parse text.
R2: For every tool call, append both the assistant message and tool_result on every iteration.
R3: Hooks are for must-enforce rules. Prompts are for style.
R4: Pass only relevant context to subagents.
R5: The available tools must include task to spawn a subagent.
R6: Multiple task calls in one response run in parallel.
R7: Use --resume to continue the main session and fork_session to branch.
R8: Use prompt chaining for fixed tasks and dynamic agents for unknown complexity.
Domain 2: Tool Design & MCP Integration
The Golden Rules:
R1: Tool descriptions need a purpose, input specifications, examples, and edge cases.
R2: Use isError: true for a connectivity failure, such as a database outage. Never return an empty array, which signals success.
R3: A proper error response is a structured object containing isError, errorCategory, isRetryable, and context.
R4: The optimal number is 4–5 tools per agent. Distribute additional tools across subagents.
R5: Never hardcode secrets. Use ${ENV_VAR} expansion in .mcp.json.
R6: Write creates, Edit modifies, Grep searches file contents, and Glob searches file names.
Domain 3: Claude Code Configuration & Workflows
The Golden Rules:
R1: Configuration layers: personal = user, team/Git = project, and module-specific = directory. The directory layer has higher precedence.
R2: Modular configuration: use @import and the .claude/rules/ directory to split large configuration files.
R3: Use a skill for isolation or tool restrictions and context: fork for a safe sandbox. Use a command for a simple shortcut.
R4: context: fork runs a skill in an isolated context, keeping exploration and changes in the fork.
R5: Use Plan Mode for large, complex, multi-file changes to review proposed actions before execution. It is excessive for simple tasks.
R6: The -p flag is mandatory in non-interactive environments such as CI/CD pipelines.
R7: Session isolation: generate in session A and review in session B. Never self-review when you need to avoid confirmation bias.
R8: The Message Batches API offers 50% savings for non-urgent tasks when a 24-hour latency is acceptable.
Domain 4: Prompt Engineering & Structured Output
The Golden Rules:
R1: Explicit criteria must be specific and measurable, rather than vague or subjective.
R2: Few-shot examples: provide 2–4 high-quality examples, including at least one edge case. Seven or more can bloat the prompt.
R3: tool_use guarantees structural correctness, such as valid JSON and fields, but does not guarantee semantic correctness.
R4: To force a specific tool, use tool_choice: {"type":"tool","name":"X"}.
R5: Specific retry: when a task fails, append a specific error message to the prompt before retrying.
R6: Multi-pass strategy: Pass 1 analyzes files individually; Pass 2 analyzes cross-file interactions.
R7: Separate sessions: generate in session A and review in session B. Never self-review when you need to avoid confirmation bias.
Domain 5: Context Management & Reliability
The Golden Rules:
R1: Case facts are immutable blocks at the start of the context. Never summarize them; this preserves critical details.
R2: LLMs often have a “lost in the middle” problem. Put critical information at the beginning or end. For very long contexts, use /compact or delegate focused tasks to subagents.
R3: Do not escalate based only on customer sentiment or a model’s self-reported low confidence.
R4: Stratified metrics: track accuracy per document type because aggregate metrics can mask category-specific failures.
R5: When information conflicts, use this hierarchy: verified → extracted → inferred → estimated. Always log the conflict.

Quizzes

Review Questions
1. PreToolUse Hooks – Regex Matching
Regex matchers without anchors (e.g., /refund/) match any tool name containing the substring, including issue_refund_note. Use ^ and $ for exact matching (/^refund$/) or a literal matcher (refund) to target only the intended tool.
2. Claude Code CLI – Non-Interactive Mode
When running Claude Code in CI/CD environments (e.g., GitHub Actions), always use -p (--print) to enable non-interactive execution. Without -p, Claude starts an interactive session and may hang waiting for terminal input until timeout.
3. Skills – argument-hint
The argument-hint field in SKILL.md frontmatter displays expected arguments in the slash-command autocomplete menu (e.g., argument-hint: [issue-number]). It improves usability without changing skill execution or validating arguments.
4. Agentic Loop – Model-Driven Decisions
After a tool executes, append its tool_result to the conversation and send it back to Claude. This allows Claude to independently decide whether to retry, call another tool, or finish, instead of relying on hardcoded application logic.
5. MCP Servers – Reserved Names
Claude Code reserves certain MCP server names, including computer-use, workspace, and claude-in-chrome. Custom MCP servers using reserved names are rejected or skipped, so they must use unique names.
6. PostToolUse Hooks – Output Replacement
Use updatedToolOutput in PostToolUse hooks to replace tool output for both built-in and MCP tools. The legacy updatedMCPToolOutput field only supports MCP tools, while additionalContext adds information rather than replacing output.
7. CLAUDE.md – File Imports
Using @path/to/file in CLAUDE.md imports the referenced file's contents into context. Wrap the path in backticks (e.g., @docs/legacy-notes.md) to display it as literal text without triggering an import.
8. Structured Outputs – False Positive Analysis
Add a detected_pattern field to structured findings to record the specific code construct or pattern that triggered each detection. This enables grouping dismissed findings by pattern, identifying false-positive trends, and improving detection accuracy.
9. PreToolUse Hooks – permissionDecision
PreToolUse hooks support three permission decisions: allow (execute automatically), ask (request human approval), and deny (block execution). Use allow for low-risk read-only operations (e.g., masked order history) and ask for high-risk irreversible actions (e.g., refunds), with identity verification enforced separately when required.
10. Research Pipeline – Parallel Subagent Execution
For independent tasks (e.g., analyzing multiple legal precedents), the coordinator should spawn parallel subagents and aggregate their results before synthesis. Keeping orchestration at the coordinator level improves latency, observability, debugging, and control compared to allowing subagents to spawn nested agents.
11. Customer Support – Resolution Before Escalation
When a customer requests human support but the issue is already confirmed as immediately resolvable, acknowledge their frustration and offer to resolve it directly or escalate. Do not automatically escalate when a verified solution is available, but respect the customer's choice.
12. Tool Choice – Enforcing Tool Execution Order
Use tool_choice: {"type": "tool", "name": "extract_metadata"} to force a specific tool call when prerequisite data must be extracted first. After receiving the result, allow subsequent turns to call dependent tools; forcing the same tool on every API request prevents the workflow from progressing.
13. Code Exploration – Tracking Function Aliases
When finding all callers of a function, first inspect its definition and wrapper modules to identify aliases, re-exports, and renamed references. Then use Grep to search for every exposed name across the codebase, rather than searching only for the original function name.
14. Structured Extraction – Handling Amendments
Design extraction schemas to preserve multiple values for amended fields, including their source locations and effective dates. This enables the system to distinguish original terms from amendments and determine which value is currently applicable instead of arbitrarily selecting one.
15. Structured Extraction – Preventing Hallucinated Values
Explicitly instruct Claude to return null when information is not directly stated in the source document, even if a plausible value could be inferred. Nullable JSON schema fields alone do not prevent hallucinations; prompt instructions must enforce evidence-based extraction.
16. Code Exploration – Incremental Architecture Discovery
For understanding large codebases, start with targeted Grep searches to locate relevant entry points, then follow imports, function calls, and dependencies incrementally. This approach minimizes unnecessary context consumption and builds an accurate architectural understanding without exploring unrelated services.
17. Research Pipeline – Dynamic Subagent Routing
The coordinator should assess each query's complexity and dynamically select only the subagents needed to complete it. Simple factual questions may require one agent, while complex research may need multiple agents, avoiding both unnecessary execution and rigid routing rules.
18. Structured Extraction – Confidence-Based Human Review
Have Claude produce field-level confidence scores and calibrate review thresholds using a labeled validation dataset. Prioritize low-confidence extractions for human review, since semantic errors can pass JSON schema validation even when all required fields are present.
19. Customer Support – Clarification Before Escalation
When a frustrated customer requests immediate human support but the issue has not yet been investigated, acknowledge their frustration and ask one targeted question to identify the problem before escalating. Avoid unnecessary investigation or repeated questions, and honor an explicit escalation request if the customer insists.
20. Code Exploration – Dynamic Task Decomposition
For debugging complex issues (e.g., intermittent HTTP 500 errors), dynamically generate investigation subtasks based on findings from each exploration step. Follow the actual execution path through routing, middleware, business logic, and database layers instead of assigning fixed parallel investigations before understanding the problem.

Practice Exams

Exam 1 · Practice date: October 12, 2026 at 04:04 PM
Key lessons from the mistakes in the first practice exam. Each note focuses on the idea that would help identify the correct answer next time.
1. max_tokens Is Not a Normal Finish
If stop_reason is max_tokens, Claude did not finish the response. Increase max_tokens and retry so you can receive the complete tool call or answer. The key is to treat max_tokens as an incomplete run, not as success.
2. Detect Completion from SDK State, Not Text
Do not decide that an agent finished because its text contains a phrase such as “Research complete.” Use the Agent SDK termination state instead. A success subtype means the loop ended normally, while error_max_turns means the run stopped because it hit the turn limit.
3. Human Escalation Needs Provenance
When sources conflict, the human reviewer needs a short structured handoff, not raw agent transcripts. Include each conflicting value, its source and date, what checks were already performed, and a suggested next step. The main idea is to make the conflict easy to verify quickly.
4. Parallelize Independent Questions
If one request contains independent research questions, split them into separate subtasks. Give each subagent the shared background it needs and launch the Agent tool calls in the same coordinator response. This improves depth and reduces latency compared with one agent doing everything.
5. Existing MCP for Standard Services, Custom MCP for Proprietary APIs
Use an existing MCP server when the integration is common and already supported, such as Jira. Build a custom MCP server when the system exposes a proprietary API with no suitable public server. The exam is testing whether you choose reuse versus custom integration correctly.
6. Use Path-Scoped Rules for File-Specific Conventions
If a rule should apply only to certain file types, place it in .claude/rules/ and use paths globs in the frontmatter. Keep one shared rule file instead of copying the same conventions into many folders. Use claude --debug to confirm the YAML frontmatter is parsed correctly.
7. Broken Frontmatter Can Make a Rule Global
A .claude/rules/ file is only path-scoped when its paths frontmatter is valid. If the YAML is broken, the rule may load in every session. Check claude --debug for parsing errors, then verify the behavior in a fresh session before and after touching a matching file.
8. Unstated Requirements Require an Interview
If missing edge cases come from requirements nobody stated, code exploration will not solve the problem. Ask the team targeted questions and write the decisions into a self-contained spec such as SPEC.md. After the design discussion, start a fresh implementation session so the coding context stays clean.
9. Errors Must Explain Cause and Retryability
isError: true alone is not enough for good recovery. The error should clearly say what failed and whether retrying can succeed, so Claude can treat a timeout differently from a protected-branch rejection. Do not rely on a local hook for policies that frequently change on the remote system.
10. Give Interdependent Fixes Together
If several fixes depend on the same signature or architecture change, describe them together in one detailed message. Claude can then plan the shared change first and implement the dependent fixes against the new design. Sending them one by one can create unnecessary rework.
11. Missing Context Is Solved by Referencing the Existing File
If Claude keeps generating duplicate tests, the problem is usually that it cannot see the current coverage. Reference the existing test file directly with @path so its full content is in context. Plan mode does not fix missing context; it only adds a review step.
12. Use Tests as the Source of Truth for Repeated Edge-Case Breakage
When each code revision fixes one edge case but breaks another, stop relying on prose alone. Write tests for all known edge cases first, then use the failing output to guide the implementation. The stable test suite becomes the exact definition of correct behavior.
13. Personal Skills Need a Different Name
A personal skill can live under ~/.claude/skills/, but a personal skill with the same name as a project skill takes precedence. If you want to keep the team’s /review and also have your own stricter version, give yours a different command name such as /review-deep. The key detail is name precedence.
14. Batch Requests Cannot Depend on Mid-Request Client Tool Calls
If a batch request needs data from a client-executed tool during the run, redesign the workflow before using Message Batches. Perform the lookup first and include the result in the batch input. This removes the interactive dependency and keeps the request eligible for batch processing.
15. JSON Schema Checks Structure, Not Meaning
A valid schema can still contain logically wrong values, such as impossible date order or swapped parties. Add semantic validation in code for cross-field rules, then retry with the exact validation errors. The exam distinction is structural correctness versus semantic correctness.
16. Find tool_use Blocks by Type, Not Position
A Claude response can contain both text and tool_use blocks, and their order is not guaranteed. Do not assume response.content[0] is the tool result. Search for the block whose type is tool_use and read the structured data from its input field.
17. Keep Global Rules Global and File-Specific Rules Scoped
Rules that must apply to every review should stay in always-loaded project context, but they can be split into imported files to keep CLAUDE.md maintainable. Rules that only matter for certain files should move to .claude/rules/ with matching paths globs. The main decision is based on scope.
18. Repository-Wide Review Criteria Belong at the Repository Root
If a rule must apply to every pull request, do not place it in a subdirectory CLAUDE.md. Put it in the repository-root CLAUDE.md and commit it to version control. This ensures every review started in that repository receives the criteria.
19. Separate Generation and Review Contexts
An agent that audits its own work in the same resumed session can inherit confirmation bias from the migration process. Run the audit in a separate claude -p session and give it only the evidence it needs, such as the diff and project rules. Fresh context improves independent review.
20. Test a New Prompt Before a Huge Batch
A brand-new prompt should be tested synchronously on a representative sample before running it across thousands of files. This catches prompt-level problems before you pay for a large batch whose results may all be weak. custom_id resubmission is useful for scattered failures in an already-tested pipeline, not for validating an untested prompt.
21. Resumed Sessions Can Contain Stale File Knowledge
If files changed after a session was paused, do not trust the old analysis blindly. Either resume and explicitly make Claude re-read the changed files, or start a new session seeded with a structured summary of the earlier conclusions. The important idea is to refresh stale context before continuing.
Exam 2 · Practice date: October 24, 2026 at 03:18 PM
Key lessons from the mistakes and marked questions in the second practice exam. Each note highlights the distinction that makes the correct answer easier to recognize.
1. Capture Everything, Then Route by Confidence
Do not suppress uncertain review findings at generation time, because real bugs may disappear with them. Report every potential issue with a confidence value, then send low-confidence findings to a separate verification pass. The key distinction is coverage during discovery versus filtering during routing.
2. Choose Grep Options from the Required Output
Use Grep's count output mode when the task asks for a match count per file; the default files_with_matches mode returns paths without counts. Add -i when the same identifier appears in different letter cases. Glob searches file names and paths, not file contents.
3. MCP Scope Precedence Replaces the Whole Entry
When the same MCP server name exists in multiple scopes, Claude Code uses the entire entry from the highest-precedence scope. It does not merge individual fields from local and project definitions. Remove the stale local entry when the shared project definition should take effect.
4. Interview Before Planning Unknown Requirements
Plan mode can inspect code, but it cannot discover product decisions the team has never made. For an unfamiliar feature with open design questions, have Claude interview the developer about behavior, edge cases, and tradeoffs, then record the agreed design in a self-contained specification. Plan and implement only after those requirements are explicit.
5. Use Stable Categories for Feedback Analytics
To learn which code patterns produce dismissed findings, require a detected_pattern field in every result. Constrain it to a stable enum so results can be grouped reliably, while keeping an other value plus a detail field for new cases. Free text alone creates inconsistent labels that are hard to aggregate.
6. Fall Back to Read and Write When Edit Cannot Be Unique
Edit requires its old_string to identify one occurrence unless replace_all is intended. If every surrounding line is identical and only one block must change, load the full file with Read and overwrite it with the corrected full content using Write. Inventing a unique anchor cannot work when none exists.
7. Let the Model Drive Adaptive Tool Loops
Use tool_choice: auto so Claude can decide after each result whether to call another tool or answer. Continue while stop_reason is tool_use and finish only at end_turn. A fixed routing table fails when the next useful action depends on evidence discovered during the run.
8. Put Long Source Material Before the Instructions
For a long prompt that still fits the context window, place the source text first and the review instructions at the end. Models attend more reliably to the end of a long input, so this ordering keeps the task requirements prominent. Splitting the source or compacting history does not fix an instruction-position problem.
9. Trace Wrapper Usage Through Exported Symbols
When unknown wrappers re-export functions under their original names, searching only known import paths misses callers. Read the source module to collect every exported function name, then Grep the repository for each name. The stable search target is the public symbol, not the route through which consumers import it.
10. Stop Context Bloat at the Tool Boundary
If tool results contain dozens of unused fields, change the tool to return only the fields the task needs. For verbose investigations, delegate the work to a subagent and return a concise summary to the main session. Prompt caching and deferred tool discovery do not reduce the context consumed by large result payloads.
11. Few-Shot Examples Must Demonstrate the Rationale
If every finding needs a justification, include that justification in the examples rather than adding only a prose instruction. Show a short one- or two-sentence rationale that cites the relevant code evidence. Examples teach the exact output pattern, while confidence scores answer a different question.
12. Delegation Prompts Must Stand Alone
A new subagent does not inherit the coordinator's conversation or tool results. Put the required file paths, prior decisions, constraints, and task boundaries directly in its prompt. Use numbered steps only when order or completeness truly matters; otherwise state the goal and necessary context clearly.
13. Revise a Bad Plan Before Approving It
If a proposed plan violates a constraint, keep the session in plan mode and explain the problem so Claude can revise the approach. Approving first and correcting individual edits later preserves a flawed design and risks inconsistent partial work. The approval checkpoint exists to fix the approach before source files change.
14. Route Dynamically with Clear Agent Descriptions
Give each subagent an AgentDefinition description that clearly states the request types it handles, then let Claude select only the agents needed. Keep quick, targeted, context-sensitive work in the main conversation and delegate self-contained tasks with verbose output. Running every subagent for every request wastes tokens even when they execute in parallel.
15. Pass Oversized Input by File Reference
Piped input to claude -p has a size limit, and changing the output format does not change that input limit. Write an oversized diff to a workspace file and reference its path in the review prompt so Claude can read the whole change set. Splitting it across separate reviews loses cross-file relationships.
16. MCP Resources Are for Data; Tools Are for Actions
Expose read-only reference material such as policy documents and reason-code catalogs as MCP resources so the agent can discover what data exists. Use a tool for operations that change state, such as updating a shipping address. Frequently changing reference data should not be copied into a static system prompt.
17. Parallel Tool Calls Need Concurrent Harness Execution
The model can request several independent Task calls in one response, but the client harness decides whether they run concurrently or sequentially. Execute the whole batch concurrently, wait for all results, and return all tool_result blocks together in one user message. Prompting for parallelism cannot repair a harness that executes the batch serially.
18. Isolate Verbose Discovery in a Subagent
For a large call-site trace, delegate discovery with an explicit goal and have the subagent return a compact list of exact locations. Its intermediate reads and search output stay out of the main context, leaving room for design and replacement work. /compact is lossy and may discard precise paths after the context is already polluted.
19. Fixed Auditable Workflows Need Prompt Chaining
When four steps must always run in order and auditors must inspect each output, implement four sequential calls with a programmatic validation gate between them. An autonomous loop can choose its own sequence, and a PostToolUse hook does not create distinct pipeline stages. Use deterministic orchestration for fixed, inspectable processes.
20. A Forked Skill Does Not See Conversation History
A skill with context: fork starts a fresh subagent whose prompt is the skill content, not the current conversation. If the task depends on debugging evidence already discussed, run the skill inline or explicitly pass that evidence into the fork. Compacting the main session does not make its history available to the fork.
21. Use Explore for Read-Only Discovery
Delegate large, read-only code searches to the Explore subagent so verbose discovery stays isolated and only a summary returns. Keep design and implementation in the main conversation because those phases share important working context and require write tools. The built-in Explore agent is one-shot and cannot be resumed later.
22. Search Broadly, Then Read for Meaning
When an identifier may be set anywhere in a repository, Grep for it across the whole codebase before narrowing the scope. Then Read the matching files and follow imports to understand the conditions around each assignment. Matching lines alone show where the text occurs, but surrounding code explains why it is set.
23. Split Tools When Each Intent Needs Different Inputs
A single tool with a hidden task selector and optional inputs invites both misrouting and missing arguments. Split it into separate tools such as scaffold_boilerplate, explain_module, and trace_symbol, each with its own required schema. Tool names make the intent visible, and schemas enforce the inputs for that intent.
24. Calibrate Confidence Before Using It for Review Routing
A model's raw confidence score is not automatically a reliable probability of error. Compare scores with past resolutions labeled correct or incorrect, then choose thresholds where actual errors concentrate. Random sampling measures overall quality, but calibrated thresholds direct limited review capacity toward the riskiest drafts.
